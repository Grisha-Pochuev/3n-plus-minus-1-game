# Proof architecture reset — 14 August 2026

Status: research strategy note. The theorem remains **OPEN — RED**.

## Decision

After the long high-return provenance investigation, do **not** make another manuscript revision whose main activity is patching Section 136 in place.

Preserve the current proof as **Track A**, because it contains a large library of valuable local mathematics and may still be repairable by a genuine occurrence-preserving lifecycle theorem. But begin a logically independent **Track B** in which the global no-DRAW proof is designed again from the reliable local lemmas rather than inherited from the current token-normalizer architecture.

This is a change of proof architecture, not abandonment of the existing work.

## Why this change is justified

Several successive audits have exhibited the same failure mode in different forms:

1. local arithmetic identities and local WIN/LOSS diamonds are often correct;
2. local proof-height inequalities are often correct;
3. the failure appears when a later finite state is treated as though its proof occurrence were automatically inherited from an earlier ranked occurrence;
4. repairing one such transition tends to move the provenance obligation to another macro boundary.

This repetition is evidence that the main unresolved issue is structural rather than a single missing residue case.

The long Pro session sharpened that diagnosis. The new finite shadow words and first-divergence lemma give real progress on transport from an exact retained `V*` occurrence, but they also expose the limitation cleanly: a strict payment in one token component cannot justify arbitrarily reseeding that same component with a later pair `(q,y)`.

The discovery that the LOSS side `y` is much more naturally compatible with proof-tree ancestry than the WIN side `q` also suggests that the symmetric pair rank used by the old architecture may not be the most natural global object.

## Track A — frozen repair problem

Keep the present proof supplement and manuscript as a research object, not as a completed theorem.

The only major question to attack in this track is:

> Can every long-return episode be represented by an occurrence-tagged finite proof forest which is fixed before branching and in which every later ranked witness is either already carried or is a certified descendant of an incoming occurrence?

Useful subtargets:

- derive a symbolic proof-compatible `V -> y` family;
- close ordinary `D=2` directly from retained `y* LOSS`;
- isolate and solve or falsify exceptional `D=2`;
- determine whether Sections 57--64 provide the missing exceptional LOSS-source transport;
- prove or refute the preinstalled shadow-forest theorem.

If this succeeds, the existing Sections 79--135 may be assembled into a sound proof. If it fails because incompatible future WIN choices force unavoidable certificate reseeding, stop patching this architecture.

## Track B — clean global proof

Start from a minimal trusted library only:

- conjugated game `A,B`;
- strict contraction `B(q)<q`;
- constant-tail coordinates and exact long-tail recurrence;
- embedded source transition identities;
- exact factor/reverse-factor identities that survived audit;
- finite WIN/LOSS proof recursion;
- locally proved outcome diamonds.

Do **not** initially import:

- the current Section 136 global rank;
- the assumption that `(q,y)` is the correct ranked pair;
- the one-shot entry bit as a global repair;
- any transition whose soundness depends on installing a newly finite witness without occurrence provenance.

Search for a new global obstruction to an infinite DRAW route.

Promising directions:

### B1. Rank native to DRAW configurations

Find a well-founded measure defined from the arithmetic/type data of the actual DRAW carrier, with finite proof certificates used only to justify local strict edges rather than stored and reseeded as the primary rank.

### B2. Minimal infinite DRAW path

Assume an infinite DRAW route with an appropriate minimality condition and prove that some recurrent tail/factor block can be shortened or replaced by a strictly smaller recurrent block.

### B3. Finite typed automaton / grammar

Use the exact tail and factor recurrences to compress an infinite arithmetic route into a finite set of symbolic control types, then prove the typed transition system has no infinite DRAW-compatible run.

### B4. Persistent proof forest from the beginning

If proof certificates are unavoidable, make the whole occurrence-tagged forest part of the state from the start rather than creating local tokens later. The global rank must compare forests themselves and must forbid replacement by a taller incompatible forest at the same numerical state.

## Track C — hostile falsification

Maintain an independent attempt to break every candidate proof.

Use bounded computation only as a falsification and discovery tool. Search for:

- large strongly connected regions;
- repeated high returns with no inherited descendant;
- exceptional short-tail rows;
- incompatible certificate choices;
- cycles in proposed abstract ranks;
- counterexamples to source, height, pair, or automaton monotonicity.

Do not infer the infinite theorem from a finite search range.

## Working rule for future manuscripts

Do not create a new public article version merely because a local gap has been patched. A new theorem-claiming manuscript should be produced only after the entire new global architecture has survived a fresh hostile audit from the original game relation to the no-DRAW conclusion.

The earlier article versions should be treated as historical generations of one evolving proof architecture, not as independent proofs from which a correct version can simply be selected.

## Immediate next action

When research resumes, begin with Track B from a clean proof file while keeping Track A available as a lemma library and as a source of counterexamples to naive ranks.

The first clean-proof question should be:

> What global object is forced to decrease along a hypothetical infinite DRAW route by the game dynamics themselves, without requiring us to manufacture a fresh proof token after seeing the future branch?

That question should guide the next phase of the project.
